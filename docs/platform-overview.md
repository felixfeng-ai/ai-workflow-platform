## 0. 一句话定位

**雅秩（VeyaWork）——把「项目协作 + 知识管理 + AI 自动化」塞进一个极简界面的轻量 AI 办公工作台。**

不是又一个「AI 聊天框」，也不是又一个「重流程项目管理软件」。它的主张是：
**用对话下达指令，让 AI 在后台把活干完，你只需要看结果。**

## 1. 平台是什么

### 1.1 三句话讲清

| 问题 | 回答 |
|---|---|
| 它解决什么？ | 团队的信息散在 5 个工具里（任务表、笔记、文档、知识库、AI 工具），AI 只是个外挂的聊天窗口，不会真的替你干活 |
| 它怎么做？ | 把「项目 / 任务 / 笔记 / 文档 / 知识库」收进一个工作台，再把 AI 变成**能操作这些数据的执行者**——生成周报、跑巡检、编排多步流程、定时无人值守执行 |
| 它凭什么不一样？ | **极简界面 + AI 原生**：所有智能体、工作流、知识问答都指向同一份业务数据；不是给旧工具贴 AI 标签，而是从数据模型开始就为 AI 执行而设计 |

### 1.2 能力地图

### 1.3 目标用户与典型场景

**目标用户**：5–50 人的小团队、独立开发者、需要「轻量协作 + 重度 AI」的知识工作者。

| 场景 | 谁在用 | 平台上怎么发生 |
|---|---|---|
| 每周写周报 | 团队负责人 | 点一次「周报」智能体 → 自动聚合本周项目、任务、笔记 → 30 秒出稿 |
| 项目健康巡检 | 技术负责人 | 「巡检报告」智能体输出完成率、高优/逾期任务、改进建议 |
| 竞品调研 | 产品经理 | 「竞品调研」智能体抓取指定页面 + 结合知识库出报告 |
| 面试准备 | 求职者 / 面试官 | 「面试押题」智能体按主题、数量、难度生成题目 |
| 团队知识沉淀 | 全员 | 上传 PDF/Word/Markdown → 直接对文档提问，答案带来源 |
| 例行自动化 | 全员 | 画布上连三步（抓取 → 分析 → 生成报告）→ 设成每天 9 点自动跑 |
| 任务不遗漏 | 全员 | 到期任务自动推站内通知 + 微信订阅消息 |

### 1.4 与其它工具的关系

雅秩**不试图替代**飞书/Notion/Jira/GitHub，而是充当**它们的 AI 执行层与轻量收口**：
项目卡片直接挂仓库地址与部署地址；知识库可扫描本地目录批量导入既有文档。
定位是「小团队的 AI 指挥台」，而不是「大企业的流程中台」。

## 3. 核心技术方案

### 3.1 可插拔 AI 引擎适配层

**问题**：AI 模型层变化极快，业务代码不应绑死任何一家。

**方案**：`app/ai/base.py` 用 `typing.Protocol` 定义最小接口——只有三个方法：

```python
class AiEngine(Protocol):
    async def chat(...) -> str
    async def knowledge_query(...) -> ...
    async def stream_chat(...) -> AsyncIterator[str]
```

两个实现：

| 实现 | 说明 |
|---|---|
| `DifyEngine` | 复用 Dify CE 的 Service API（headless 调用），可白嫖 Dify 的可视化编排与运营能力 |
| `OpenAICompatibleEngine` | 走标准 `/chat/completions`，适配 DeepSeek、通义千问等一切兼容端点 |

`get_ai_engine()` 工厂按 `AI_PROVIDER` 环境变量切换，**业务层零改动**。

**降级行为**（对外演示的关键）：
- 未配置 API Key → 抛 `AiEngineUnavailable`
- 普通端点（chat / knowledge）返回 **503** 并给出明确提示
- 流式端点（副驾 / 写作）因响应头已发出，改为在事件流中输出 `error` 事件后优雅收尾，HTTP 状态仍为 200

### 3.2 智能体体系

**4 个内置智能体**：

| Key | 名称 | 能力 |
|---|---|---|
| `weekly_report` | 周报生成 | 聚合本周/上周/本月的项目、任务、笔记，成稿 |
| `inspection_report` | 巡检报告 | 完成率、高优任务、逾期任务、改进建议 |
| `interview_questions` | 面试押题 | 按主题/数量/难度生成题目 |
| `competitor_research` | 竞品调研 | 可选抓取指定 URL 正文，结合知识库出报告 |

**自定义智能体**：用户在界面上写一段 Prompt + 定义参数表单（`param_schema` JSON），
即得到一个可运行、可编排、可定时的智能体——**不需要写一行代码**。

**统一解析（设计要点）**：内置智能体是 Python 类，自定义智能体是数据库记录，二者形态不同。
`resolve_agent(db, key)` 先查内置注册表、再查数据库，把它们**适配到同一个 `Agent` Protocol**，
因此自定义智能体在「单独运行 / 工作流步骤 / 定时调度」三条路径上行为完全一致。

**调用接缝（反向适配）**：智能体拿到的不是裸的 `AiEngine`，而是包了一层的 `AiEngineChatModel`
（LangChain `BaseChatModel` 子类）。方向是**把自研 Protocol 适配进框架**，而不是用
`langchain_openai` 替掉它 —— 平台的价值之一就是 Dify / 任意 OpenAI 兼容模型可插拔，
换成框架自带的 provider 等于把这份能力交出去。同步 `invoke` 显式报错（引擎只有异步接口），
不做静默降级。

**后台执行模型**：触发即返回 `202` + `run_id`，`asyncio.create_task` 后台执行，
状态机 `pending → running → succeeded/failed` 落库，前端轮询。完成或失败会写一条站内通知。

**`tools.py` 的 SSRF 防护**（竞品调研抓取网页时）：拒绝私有/保留地址、逐跳校验重定向、禁止携带凭据、限制读取长度。

### 3.3 工作流引擎

| 能力 | 实现 |
|---|---|
| 可视化编排 | React Flow 画布，左侧 Agent 调色板，右侧参数面板；一个节点可有多条出边（分支）与多条入边（汇聚），连线时可编辑分支条件 |
| 执行模型 | `steps` + `edges` 编译成一张 **LangGraph `StateGraph`**：节点 = 一步，边 = 连线；无条件多出边即并行扇出 |
| 条件分支 | 结构化条件 DSL（op 白名单：文本/空值/数值/布尔组合），**不做表达式求值**；走哪条路由 LangGraph 的 `add_conditional_edges` 决定 |
| 结果传递 | 递归插值 `{{prev_output}}`（**图上的前置节点**输出，多前置时拼接）、`{{step.N.output}}`，支持 dict/list 嵌套替换 |
| 状态持久化 | 自研 `SqlAlchemyCheckpointer`（`BaseCheckpointSaver` 子类），每步一份 checkpoint，落 `langgraph_checkpoints` 表 |
| 断点续跑 | 失败后 `POST /runs/{id}/resume`：复用同一 run 与 thread，**已完成的步骤不重跑**，只重试失败那步及其下游 |
| 失败策略 | 任一步失败即终止；已完成步骤的输出从 checkpoint 快照回填落库，前端可见「跑到哪一步挂的」 |
| 定时执行 | `cron` 或 `interval_minutes` 二选一 |
| 前端体验 | 定时配置**白话化**（每 N 分钟 / 每天 / 每周），cron 表达式折叠进「高级」；空画布有三步引导；内置模板一键起步（含分支模板） |

**为什么是 LangGraph，而不是继续手写 for 循环**：手写循环要自己实现条件路由、并行调度、汇聚时机、
中断恢复四件事，其中「汇聚节点何时可以跑」正是最容易写错的一处。LangGraph 把 super-step 调度、
channel 归约、checkpoint 协议都固化成框架契约，业务代码只需要声明节点与边。

**为什么条件用结构化 DSL 而不是表达式字符串**：`steps`/`edges` 由登录用户提交并原样落库，
再被定时调度器在无人值守时自动重放。让用户写 `"风险" in {{prev_output}}` 然后 `eval`，
等于把服务端任意代码执行权交出去；自研表达式解析器也只是把注入面挪个地方。
白名单 op 把「能表达什么」事先钉死，求值过程不碰 Python 运行时。

**汇聚节点要求各分支「等深」**（最反直觉的一处约束）：LangGraph 里一条边写的是
`branch:to:<target>` 这个 `EphemeralValue` 通道，同一 super-step 内的多笔写会合并，
**跨 super-step 不会**——若两个分支深度不同，汇聚节点会在先到的那个分支上先跑一次再被触发一次，
模型白烧一遍。真正「等齐所有入边」的 `NamedBarrierValue` 语义是「所有前置都必须完成」，
条件分支下被跳过的那条永远不会完成，if/else 汇聚直接死锁。两种语义买不到两个场景，
所以选 `EphemeralValue`（保住 if/else 合并这个高频用法），并在**保存时把不等深的汇聚判为非法**。

**调度单例不变量**（踩过坑的加固点）：固定 job id `wf-<id>` + `replace_existing=True` + `max_instances=1` + `coalesce=True`，
保证服务重启、重复调用、任务堆积时都不会重复注册或并发执行同一个工作流。

**设计取舍**：`edges` 为 `NULL` 即「线性」，由后端按 `steps` 顺序自动连成一条链 ——
存量工作流不改一行数据即保持原行为，`node_id` / `position` 继续作为元数据透传落库。

### 3.4 RAG 知识库

```
上传(md/txt/pdf/docx) 或 扫描本地目录
        │
        ▼
   parsers.py    → 纯文本（UTF-8 → GB18030 兜底；PDF 用 pypdf，DOCX 用 python-docx）
        │
        ▼
   chunker.py    → 按空行 + Markdown 标题切段，短段合并至 600 字，超长硬切
        │
        ▼
 document_chunks → 落库（冗余 project_id 免 join，seq 有序）
        │
        ▼
   retriever.py  → 关键词检索：ASCII 词 + 中文滑动二元组，LIKE 计分取 top-5
        │
        ▼
   prompts.py    → 拼装上下文，要求只依片段作答并标注来源 [文档名 #段落号]
```

**两个务实决策**：
1. **不引入向量数据库**——关键词检索 + 中文二元组切词在几千篇文档量级下效果足够，且零依赖、可解释、可调试。`Retriever` 是 Protocol，未来换 embedding 检索不动上层。
2. **检索为空则短路**——不调用 LLM，直接返回「知识库中没有相关内容」，省钱且杜绝编造。

### 3.5 AI 副驾（对话式指挥）

这是平台「对话式指挥」叙事的技术落点。`POST /api/copilot/chat`，SSE 流式。

**意图路由不依赖原生 function calling**——先用一次非流式调用让模型输出 JSON 意图，
再用正则抓取 + **动作白名单校验**（非法一律回退为普通问答）。好处是 Dify 与 OpenAI 兼容两个引擎通用。

可调度的动作：

| 动作 | 行为 |
|---|---|
| `answer` | 普通问答（流式） |
| `knowledge` | 走 RAG，答案带来源 |
| `run_agent` | 同步等待智能体结果（90 秒超时兜底） |
| `run_workflow` | 提交后台执行，返回 `run_id`，前端轮询 |
| `create_task` | 直接建任务 |
| `create_project` | 直接建项目 |
| `help` | 能力说明 |

上下文注入当前租户的智能体 / 工作流 / 项目清单，因此模型「知道你有什么」，能给出可执行的建议。
所有查询与创建按 `tenant_id` 过滤，跨租户一律 404。

### 3.6 AI 写作

`POST /api/writing`，SSE 流式，三种操作：**续写 / 润色 / 总结**。
无数据库依赖的纯文本变换，各配专属系统提示词。
超过 12000 字时：续写取尾部作上下文；润色/总结返回 `text_too_long` 并建议分段。

### 3.7 多租户与权限

| 维度 | 方案 |
|---|---|
| 隔离键 | 每个用户注册时默认分配独立 `tenant_id`；并入团队后共享同一 `tenant_id` |
| 查询约束 | 所有实体查询/写入强制按 `user.tenant_id` 过滤 |
| 越权响应 | 不存在与跨租户**统一返回 404**，不泄露资源存在性（IDOR 防护） |
| 角色 | `owner` / `member` / `readonly` 三级，由 `require_role(*roles)` 依赖工厂施加于写端点 |
| 成员迁出 | 移除成员时为其分配**新的独立租户**，历史通知仍可见（通知按 `user_id` 查，不按租户） |
| 邀请 | `code` 唯一、7 天有效、一次性使用，注册时带码即并入团队 |

### 3.8 通知中心与到期提醒

**通知 = 用户级收件箱**（按 `user_id` 查询，而非 `tenant_id`）——这是刻意的设计：
被移出团队的用户仍能看到自己的历史通知，符合直觉。

5 类事件：`agent_run`（智能体完成/失败）、`workflow_run`（工作流完成/失败）、
`team`（加入团队/角色变更/被移出）、`knowledge`（文档入库/目录扫描汇总）、`due_reminder`（任务到期）。

**两个工程不变量**：

1. **通知失败绝不能拖垮主流程**。`create_notification` 用 SAVEPOINT（`db.begin_nested()`）隔离，
   全量吞异常仅记日志，且**绝不自行 commit**——提交时机由调用方既有的 commit 边界决定。
   这样「运行状态落库」永远不会因为通知写失败而回滚。
2. **到期提醒按天幂等**。唯一列 `dedupe_key = due:{user_id}:{task_id}:{date}` + 应用层预查双保险。
   每天 9/15/21 点扫描（Asia/Shanghai 时区），逾期任务次日会再次提醒但当天只提醒一次。

前端为 30 秒轮询未读数 + 面板内乐观更新（点开即置已读，请求失败下次刷新校正）。

### 3.9 前端工程：demo / live 双模式数据层

**这是整个前端最值得讲的一个设计。**

```
                   lib/view.ts
        DataLayer = typeof demoApi   ← 接口契约的唯一事实源
                   ╱          ╲
          lib/api.ts          lib/demo.ts
        （真实后端）          （全内存 mock，含演示数据）
                   ╲          ╱
              页面组件只依赖 DataLayer，不感知数据来源
```

- `mode.ts` 用 1.5 秒超时的 `fetch('/health')` 探测后端，决定 `live` 还是 `demo`（结果缓存）
- `api.ts` 与 `demo.ts` **逐方法镜像**（含两个 async generator 流式方法）——漏一个 `tsc` 直接报错
- 演示模式下顶部显示「演示模式」横幅，说明数据为样例

**这个设计带来三件事**：
1. **对外演示零风险**——后端没起、网络不通、客户现场无网，界面依然完整可交互，流式打字机效果都有
2. **API 契约被 mock 反向锁定**——改后端接口必须同步改 mock，类型系统强制两边一致
3. **同一套 UI 既是销售 Demo 也是生产界面**——不存在「演示版」与「真实版」的漂移

### 3.10 设计体系

**唯一事实源 `DESIGN.md`**，方向「黑金旗舰（Obsidian）」：深炭黑 + 香槟金，奢华而有秩序的「AI 指挥中心」。

- **4 套主题**：`obsidian`（黑金旗舰，默认）/ `aurora`（通透光感）/ `deepspace`（深空蓝金）/ `crystal`（晶界金）
- **Token 全走 CSS 变量**，`html[data-theme="<id>"]` 整组切换，Tailwind 映射为 `rgb(var(--x)/<alpha>)` 支持透明度修饰
- **金色是唯一灵魂色**——主色只允许金，辅助色 ≤2，禁止紫蓝渐变与彩色光晕

> 工程陷阱记录：Tailwind v3.4 的 Lightning CSS 会把同文件内的 `var()` 静态解析成字面量导致切主题失效，
> 因此 token 定义放在 `index.html` 的内联 `<style>`（Tailwind 管道之外）。

## 5. 部署与运维

**架构**：单台阿里云 ECS + Docker Compose，5 个服务（postgres 16 / redis 7 / backend / frontend / nginx）。

- **所有业务端口仅绑定 `127.0.0.1`**，对外只暴露 nginx 网关
- nginx 统一路由：`/` → 前端 SPA，`/api/` → 后端（读超时 120s），`/health` → 后端，`/assets/` → 长缓存 1 年
- 隐藏 `/docs`、`/openapi.json` 与隐藏文件；配置安全响应头；`client_max_body_size 50M`
- **前端同源部署**（构建时 `VITE_API_BASE=""`），因此**完全没有 CORS 配置**——少一类线上故障
- 后端容器入口自动执行 `alembic upgrade head`，迁移是唯一的建表事实源
- **Dify CE 可选**：走独立 `compose.dify.yml` + `profiles: ["dify"]` 门控，默认不启动，需要时一条命令启用
- HTTPS 块已预置（certbot 证书挂载即可启用）

**CI/CD 链路**：

```
push main
   │
   ├─ CI：后端 pytest（内存 SQLite 单测 + 真实 PG 走迁移的集成测试）+ 前端 npm run build
   │
   └─ Deploy：GitHub Actions → appleboy/ssh-action → 服务器执行 cicd-deploy.sh
        git fetch + reset → docker compose build + up -d → 轮询 /health（最长 120s）
        → 逐服务状态检查 → 校验网关 /api/ 返回 401
```

**回滚**：`git reset --hard <上一提交> && bash cicd-deploy.sh`，一条命令。

**当前线上状态**：`http://47.116.138.61:8080` — `/health` 返回 200。

## 7. 技术亮点（对外可讲的六个点）

1. **可插拔 AI 引擎层** — 三个方法的 Protocol，Dify 与任意 OpenAI 兼容模型（DeepSeek/通义等）自由切换，业务代码零改动。客户已有模型资产可直接接入，不被锁定。
2. **零代码自定义智能体** — 写一段 Prompt + 定义参数表单即得到一个智能体，且能直接进工作流、能被定时调度。**这是最容易被客户「哇」到的一点**。
3. **可视化工作流 + 条件分支 + 断点续跑** — 画布连线编排多步 AI 任务，一条边可带条件（走哪条路由后端判定），多条无条件出边即并行执行，`{{prev_output}}` 自动传递上一步结果；每步状态落 checkpoint，失败后可**只重跑失败那一步**，前面的模型花费不白花。设成定时后每天自动出报告 —— 产品叙事的落点：**「定时跑完 AI 只收结果」**。
4. **demo/live 双模式数据层** — 后端不在也能完整演示，API 契约被类型系统反向锁定。**对销售与交付是降维打击**：任何环境、任何网络都能演。
5. **极简技术栈带来的私有化优势** — 一个 Docker Compose 文件、一台 2C4G 服务器即可完整私有化部署，一条命令回滚。不依赖任何云服务、向量数据库或消息队列，**可以部署在完全离线的内网**。
6. **AI 原生的数据模型** — 不是给旧工具贴 AI 标签：项目、任务、笔记、文档、知识库从一开始就是 AI 可读写的对象，副驾能在同一份数据上理解与执行。

### 9.5 介绍时的三个禁忌

1. **不要罗列功能清单**。功能表是最没有说服力的介绍方式。永远从「你现在每周花几小时做这件事」这个痛点切入，再落回功能。
